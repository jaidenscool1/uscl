## Performance (Mario Kart World, i5-10600K + RTX 4060 8 GB, Linux, NVIDIA 615.78)

Grand Prix race driven by the debug server, fps averaged over 5 s chunks. "Racing" is the part after the start (the game picks 60 or 30 fps per frame; it drops toward 30 when a frame misses 16.7 ms).

| Build | Pre-race | Racing | Frames over 100 ms per run (boot + menus + race) |
|---|---|---|---|

| 2026-11-15: + upstream `30181ba05` + 0007, plain Release build | 60 | 35.4–35.6 | 16–22 |
| same, built `-march=native` + PGO + ThinLTO for video_core (0008, recipe below) | 60 | 41.2–42.0 | 15–21 |

Where a racing frame's time went before 0009 (perf, 20 s of racing on the optimized build): the GPU back thread, which runs the game's GPU methods and records the host draws, is ~82% busy (~8% of that spin-waiting), about 18.5 ms per frame against 16.7 ms for 60 fps. The emulated CPU cores are ~50% busy each, the GPU front thread ~59% and the host GPU ~35–40%. The back thread's time is spread thinly: draw setup is ~59% of it (binding textures, uniform/storage buffers and descriptors per draw), with no single function above a few percent. 60 fps racing needs that thread (and then the game's own CPU work, ~14–18 ms per frame in the JIT) under 16.7 ms.

Measured 2026-11-16 (`docs/HANDOFF-gpu-rewrite.md`): almost every draw changes its bindings (pipeline same as the previous draw's 30% of the time, a stage's textures 26%, nothing changed 1.9%), so skipping "unchanged" draws gains little; individual resources are stable (texture descriptors 98%, samplers 100%), so caching per resource helps (0013). Binding small uniform buffers straight from guest memory instead of copying them is unsafe: ~10% of them change before their command buffer is submitted, and ~0.37% are rewritten by the game's CPU code before the host GPU finished reading them.

All draws run on one GPU channel (channel 1: ~98,000 draws/s while racing, ~4.9 µs each; channel 2 runs only compute, ~5% of the back thread's work; Switch Sports draws only on channel 1 too), so one back thread per channel would parallelize almost nothing. Only ~6% of the back thread's time (pipeline selection, descriptors, dynamic state, recording) could move to a second stage: the rest reads guest memory or the texture/buffer caches in command order.

Tried and not kept (measured in the same race): guest memory in 2 MiB pages (`madvise(MADV_HUGEPAGE)` on the memfd backing and the fastmem views: ~6.7 GB mapped huge, racing 38.3/38.2 vs 40.6/38.0, +0.6 GB RSS), small uniform buffers compared and copied in place instead of through a scratch copy (39.9/36.8 vs 39.6/38.9), `-fsplit-machine-functions` + ext-TSP block placement on top of PGO (45.5/45.6 vs 47.4/48.4), `EDEN_NX2_FRAMES_AHEAD=0` + `EDEN_NX2_BACK_WAIT=1` (racing 22–26 fps), `EDEN_NX2_FRAMES_AHEAD=1` (racing better, 38–48, but pre-race 33–46 instead of 60, and 1 of 2 runs hung when a movie ended), `EDEN_NX2_IMAGE_ALLOCATION_REUSE=1` (no measurable change), small images sub-allocated instead of NVIDIA's preferred dedicated memory (racing −1 fps, more hitches, VRAM peak 7.9 GB instead of ~6.4 GB), and whole-program ThinLTO (see 0008). Mario Kart World's upstream preset turns reactive flushing off: 75× fewer trapped CPU reads, no fps change; it is a per-game setting, so it is not applied.

## Probes, benchmark harness, docs

- `probes/` (not applied by default; `git am` on top of 0013): 0001 adds `EDEN_NX2_BIND_STATS` per-draw change probes (stage bindings, texture handles, pipeline) hooked into `RasterizerVulkan::Draw`, and `EDEN_NX2_PROFILE_FAST=1` (keeps the fast method path under `EDEN_NX2_GPU_PROFILE`, whose slow path crashes in `QueryCacheBase::CounterReport`). 0002 adds `EDEN_NX2_AB=<Nx2Perf switch>`, which flips that switch every 20,000 draws and logs draw cost with it on and off inside one race (sees 1–2% changes that fps A/Bs, ±6% per run, cannot), and `EDEN_NX2_UBO_LIVE_PROBE` (the uniform measurement above).
- `bench/`: the scripts behind every number here (one MKW Grand Prix race per run through the emulator's debug server, interleaved A/Bs, the Switch Sports regression check, perf analysis). Set `USCL_GAME` / `NSR_GAME` to the games' `exefs/main`.
- `docs/HANDOFF-gpu-rewrite.md` (latest measurements and decisions), `docs/HANDOFF-perf.md` (earlier history), `docs/PROMPT-nvidia-gpu-passthrough.md` (prompt for the next project: running the guest's NVIDIA command streams on the host NVIDIA GPU instead of translating each draw).

## Keeping up with upstream

The working fork is `~/src/eglantine`, branch `uscl` (origin = upstream). `python3 tools/emu-sync/emu-sync.py check eglantine` reports new upstream commits and whether any touch a file we changed; `apply --build eglantine` merges the clean ones and rebuilds `build-uscl`. After a merge, regenerate this folder: cherry-pick our commits onto `origin/nx2-experimental` in a scratch worktree, check `git diff uscl HEAD` is empty, and `git format-patch origin/nx2-experimental..HEAD`. Applying this folder with `git am` to the pinned base gives a tree identical to `uscl` (checked 2026-11-15).

## Patches
- 0001 ports uscl-eden 0012 to Eglantine's SDL3 input driver: with `USCL_AUTO_PADS` set (the home screen sets it when Automatic Controller Setup is on) every connected game controller becomes players 1–8 in connection order, mapped with Eglantine's own per-controller defaults. Without it, player 1 stays on the keyboard.
- 0002 skips a wasted texture upload: when the copies that build a joined image already write every level and layer (Mario Kart World joins three GPU-written 2048×2048 depth targets into a 3-layer array every few seconds), JoinImages no longer unswizzles and uploads the old guest-memory contents first. Mario Kart World race on an RTX 4060: those uploads drop from ~40 per run to 1, about +4% average FPS in an A/B, no visual change.
- 0003 fixes most of the stutter: upload staging and the stream buffer move to host-cached memory on NVIDIA's proprietary driver. Uploads unswizzle into staging in 16-byte pieces; into write-combined/BAR memory that ran at ~270 MB/s in the emulator (RTX 4060, PCIe 3.0), stalling the GPU thread 10–20 ms per streamed texture. Cached: ~8 GB/s. Mario Kart World race: ~23 → 30–44 fps, p99 frame time ~140 → ~50–70 ms, frames over 50 ms per 10 s 142 → 26–37. `USCL_CACHED_STAGING=0/1` forces it off/on (other drivers keep upstream's choice).
- 0004 unswizzles textures over 2 MiB on several threads: output lines are independent, so the GPU thread splits them across a small pool (a third of the host's threads, 1–6, so smaller CPUs keep theirs for the emulated cores). Byte-identical output (round-trip test); Mario Kart World race +10% average FPS (38 → 42–43).
- 0005 drops a per-block cost in the CPU JIT: with perf maps off (the normal case) every compiled block still took a global lock, looked up `PERF_BUILDID_DIR` and formatted the block's name, with all cores compiling at once while a game boots. 17.8 → 16.8 µs per block.
- 0006 shares the JIT's code cache between a process's cores. Each core had its own and compiled every block it ran: Mario Kart World compiled 1.55M blocks for 511k distinct ones, and its boot stutter was almost all compilation. Per-core values the code used to embed are read from each core's state, blocks link through 8-byte slots set with atomic stores (no live instruction is rewritten), each core keeps its own fast-dispatch table, and invalidation keeps the code space. Mario Kart World, boot to race: 510k blocks compiled instead of 1.55M, frames over 100 ms 20–26 instead of 29–40; Switch Sports Resort runs as before. `USCL_SHARED_JIT=0` gives every core its own cache again.
- 0007 stops sparse texture binds from stalling the GPU thread. Every `vkQueueBindSparse` (the zero block, tiles and layers) waited for a fence on the CPU, i.e. until the graphics queue drained: ~33 ms per bind in Mario Kart World's terrain streaming (a GPU-side wait measured ~5 ms per bind). The bind now signals a semaphore that the scheduler attaches, at every stage, to the next batch it submits, whatever submits it, and keeps until that batch completes. An earlier version waited for the semaphore only in an explicit flush after the uploads; a staging request that flushed between the bind and the uploads then sent them unprotected, which matches the corrupt textures seen with the frame spike recorder on. None of the 48 runs logged since (recorder off) shows the corruption's `Invalid MSAA mode` assert or a broken texture in the screenshots checked.
- 0008 adds `USCL_VIDEO_CORE_LTO` (CMake option, off by default): ThinLTO for `video_core` only, the GPU threads' code. A whole-program ThinLTO build crashed Switch Sports Resort once on `this == GetCurrentThreadPointer(kernel)`: the core's guest threads are fibers that resume on other host threads, and a `thread_local` read inlined across files can be reused from before the switch. The GPU threads have no fibers.
- 0009 removes a wait from every present while GPU channels stay suspended. A present waits for its own frame unless a channel is suspended, then falls back to the previous frame after a 3 ms grace. Mario Kart World's channels are suspended at every racing present, so each frame paid the grace (~3.2 ms "blocked on the GPU fence") before the same fallback. After 8 presents in a row that gave up, the present gives up at once; one that sees its frame finish restores the grace. Fence wait ~3.2 ms → ~0–0.3 ms per frame; racing +9% in an interleaved A/B. `USCL_PRESENT_GRACE=fixed` restores the old behaviour.
- 0011 is upstream's staging buffer release fix (branch `fix/vk-staging-release`, not yet in `nx2-experimental`): a staging buffer is freed only after 60 frames unused, every size class is checked each frame (at most 32 frees), and sizes above 1 MiB round to quarter steps. Before, any buffer the GPU had finished with was freed, so buffers taken every frame were created again: 4.7% of the GPU back thread's time was `vkAllocateMemory` for them, now 0. Our own version (keep 600 frames, nothing else) measured 2–4 fps worse; this one +2.8% (noise level).
- 0012 gives the GPU back thread (the frame's critical path) and the front thread a physical core each, and every other thread the remaining cores (Linux; a helper re-applies the masks every second; skipped when fewer than 4 logical CPUs would be left). `USCL_BACK_CORE=1` places only the back thread (no gain measured), `=0` turns it off. Mario Kart World racing +2.2%, minimums +2–3 fps.
- 0013 adds Nx2Perf switch `image_view_memo` (default on): a texture whose descriptor is unchanged and whose view this slot already prepared this frame skips re-preparing it while no image gained CPU-modified/alias state or was deleted (a global epoch bumped at every such site). Verify mode (`EDEN_NX2_PERF_VERIFY=1`) runs the old path and logs any memo hit that needed preparation: none in a race.
- 0010 fixes Switch Sports Resort's freeze. The emulator runs each command list from a copy of its words taken at submit, and copied every queued list again from memory each time a channel resumed from a semaphore wait (for games that write a list after submitting it, then release the wait from the CPU: Mario Kart World, Pokopia, Hyrule Warriors: Age of Imprisonment per upstream's commits). Switch Sports' compute channel resumes ~4 times a frame inside one list while the game refills its 2-frame command ring, so a later resume re-read an acquire already rewritten for the frame after next (a probe logged entry #14's value changing from this frame's to the next-but-one's at one resume) and the 3D and compute channels deadlocked until the present's 15 s timeout. Now a list's copy is settled once, at the first resume after it is queued: copied again only if no GPU release met the wait (the CPU released it), kept as submitted if another channel's release did (that release isn't ordered with the game's writes; `Nx2SemaphoreWaiters` latches waiters only on GPU writes). Copying once regardless got past the movie but crashed later (a 3D list re-read after the compute channel's release held the next frame: garbage methods, invalid KeplerMemory registers). Result: Switch Sports runs 320 s (intro, island tour, customization, main sports menu) at 59.8 fps with no garbage method or channel wait, where it froze at ~52–63 s in every run before. Mario Kart World: same racing fps, rendering unchanged, no garbage method; all its resumes (15,000 counted) follow GPU releases. `USCL_SNAPSHOT_REFRESH=once|never|every` overrides it (`every`: as before).

Settings used on the test PC (per profile, not set by USCL): GPU accuracy Low (Mario Kart World racing ~25 → ~33 fps on the 2026-11-14 build, renders correctly), docked mode, 16× anisotropic filtering, SMAA. Leave `EDEN_NX2_SPIKES` (the frame spike recorder) off outside debugging (see 0007).

## Open issues

- **Switch Sports Resort** (fixed by 0010, see Patches): a Tennis match loads and renders at 60 fps but waits for a motion swing to serve (no motion input mapped yet); online play is untested. Two experiments that did not fix the freeze, for the record: letting the present skip its wait for the previous frame when every channel is suspended (bounded to one or two frames in flight; the next frame stalled the same way), and re-reading only after the first resume (crashed later, see 0010). Probes: fork branch `uscl-semprobe2` (`USCL_SEM_WRITE_WATCH=1` logs every acquire, release and command-list refresh on the queue semaphores, and where each entry's words came from).
- **Mario Kart World racing below 60 fps:** the GPU back thread (see Performance); 60 fps needs ~25–30% less of its time per frame. Per-resource caching looks worth ~10% more; the rest needs moving work off that thread or a different approach (`docs/PROMPT-nvidia-gpu-passthrough.md`). 1–1.8 s hitches remain when the game boots and when a race loads (one very large first frame of ordinary per-draw work, texture creation and shader builds).

## Build (Linux)

Same dependencies as uscl-eden (Qt 6 incl. Charts, SDL3 is bundled, FFmpeg, OpenSSL, clang). On a checkout of the pinned base (or `uscl` in the working fork, which already has them):

```
git am <uscl>/uscl-eglantine/patches/*.patch
cmake -S . -B build-uscl -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
  -DENABLE_QT=ON -DYUZU_CMD=ON -DYUZU_TESTS=OFF -DBUILD_TESTING=OFF -DYUZU_ROOM=OFF -DYUZU_ROOM_STANDALONE=OFF \
  -DENABLE_WEB_SERVICE=OFF -DENABLE_UPDATE_CHECKER=OFF -DUSE_DISCORD_PRESENCE=OFF -DYUZU_USE_BUNDLED_FFMPEG=OFF \
  -DYUZU_DISABLE_LLVM=ON -DVulkanHeaders_FORCE_BUNDLED=ON
cmake --build build-uscl --target yuzu yuzu-cmd
```

Without a system Qt Charts, add `-DQt6Charts_DIR=<prefix>/lib/cmake/Qt6Charts -DCMAKE_PREFIX_PATH=<prefix>` pointing at an extracted `qt6-charts` package in a lasting location (the binary's RUNPATH keeps that path). Put `build-uscl/bin/eglantine` on PATH as `eglantine` or set `USCL_SWITCH2_CORE`. The upstream release AppImage also runs, but without 0001 (keyboard only).

### Optimized build (what the racing numbers above use)

Tuned for the CPU it is built on (`-march=native`: don't copy the binary to an older CPU), profile-guided (PGO), ThinLTO for `video_core` only; needs clang and lld. PGO takes two builds:

1. Instrumented build: the configure line above in another directory with `-DCMAKE_C_FLAGS="-march=native -fprofile-generate" -DCMAKE_CXX_FLAGS="-march=native -fprofile-generate" -DCMAKE_EXE_LINKER_FLAGS="-fuse-ld=lld -fprofile-generate"`.
2. Train it: run a game from it with `LLVM_PROFILE_FILE=<dir>/eg-%p.profraw` (no `%c`: continuous-mode files came out unreadable) and quit normally so the profile is written. Ours is one Mario Kart World Grand Prix race. The instrumented build fails to decompress Switch Sports Resort's code (`DecompressDataZBIC`); the final build loads it normally.
3. `llvm-profdata merge -o eglantine.profdata <dir>/*.profraw` (`llvm-profdata` is in Arch's `llvm` package).
4. Final build: the configure line above plus `-DUSCL_VIDEO_CORE_LTO=ON -DCMAKE_C_FLAGS="-march=native -fprofile-use=<path>/eglantine.profdata -Wno-profile-instr-unprofiled -Wno-profile-instr-out-of-date -Wno-backend-plugin"`, the same for `CMAKE_CXX_FLAGS`, and `-DCMAKE_EXE_LINKER_FLAGS="-fuse-ld=lld -flto=thin -fprofile-use=<path>/eglantine.profdata"`. CMake's `ENABLE_LTO` is not used: it insists on `llvm-ar`, and it would put the core under LTO too (0008).

A profile made before later source changes still applies to the unchanged code (clang warns about the rest, silenced above); retrain after large upstream merges.
