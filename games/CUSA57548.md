# Call of Duty: Black Ops II (PS4, CUSA57548)

Runs on the USCL shadPS4 fork (`uscl-shadps4`) with shadNet (`uscl-shadnet`) and uscl-dw (title 2430, auth3 on
TCP 443). Two-PC public matches over the bridge (`bo2ps4` preset) work. PS3 version: `BLUS31011.md`.

## Crossplay with PS3 (work in progress)
Three layers between the games, each must be translated by the bridge:
1. **Peer DTLS** (Demonware bdDTLS, below): both builds encrypt game UDP. Instead of the bridge ending it, our own
   game patches turn the DATA encryption off ("USCL: plain peer data"); the Steam tunnel encrypts between PCs.
2. **Lobby / party messages and the connect string** (`protocol` 2093 on PS3, 2097 on PS4, `netfieldchk`).
3. **In-game messages**: snapshots and entity fields (same fields, different order and encoder ids, see
   `netfields_*.txt` in the RE folder). **Huffman: same on both** (2026-10-28): the 256 byte counts (sum 2154224,
   byte 0 = 274054) are identical, PS4 `0x0094b500` (LE, built by `FUN_00386850`) and PS3 `0x009331c8` (BE, lazy
   init in `0x0032a684`), same build calls, so no translation there. Asset ids not compared yet.

### Peer DTLS (from PS4 codmp.elf; addresses are Ghidra's, game = +0x400000)
Every field is written by bdBytePacker, a raw memcpy, so it is in **native byte order**: little-endian on PS4,
big-endian on PS3.

- Header (6 bytes, `0x8a21a0`): u8 type, u8 version = 2, u16 vtag, u16 extra (sequence number in data).
- INIT, type 1 (`0x8a2c40`, serializer `0x8a1fa0`): header (vtag 0) + u16 init tag + 8-byte secID. Sent up to 6x.
- INIT_ACK, type 2 (`0x8a4b90`, `0x8a5ad0`): header (vtag = the peer's init tag) + u32 time + u32 cookie MAC +
  5x u16 (tags) + bdAddr blob (<= 0x88 bytes) + 8-byte secID. The cookie MAC is 4 bytes of HMAC-SHA1 keyed with a
  16-byte per-process secret; only the side that made it checks it (`0x8a4e10`).
- COOKIE_ECHO, type 3 (`0x8a4970`, `0x8a2660`): header + copy of the INIT_ACK body + 0x25 bytes (not decoded
  yet) + secID + 100-byte ECC public key of the initiator (libtomcrypt `ecc_export`, zero padded).
- COOKIE_ACK (`0x8a52d0`): the responder's 100-byte ECC public key. Handled in `0x8a40f0`.
- Session key (`calculateSharedKey`, `0x8a5090`): secKey = bdSecurityKeyMap[secID] (16 bytes);
  key = Tiger-192(ECDH secret (28 bytes, a 224-bit curve) || secKey), 24 bytes, used as the 3DES key.
- DATA (`0x8a5f70` / `0x8a64b0`): header (16-bit sequence) + 8-byte MAC + 3DES-CBC of [u16 length + payload]
  padded to 8. IV = first 8 bytes of Tiger-192(32-bit sequence, native order), the 16-bit number widened by
  bdSequenceNumber (`0x8ce640`). MAC = HMAC-SHA1(key) over header + ciphertext, first 8 bytes.
- PS3 (`t6mp.elf`) uses the same library: `calculateSharedKey` at `0x7fa3e4`, bdECCKey at `0x86bd74`/`0x86be28`.
  Only the byte order differs.
- **Plain peer data (2026-10-29), PS4 done:** `uscl-shadps4/mk_mm_patch.py` patches DATA only: send `0x8a62df`
  `call [rax+0x10]` (in-place 3DES) -> `mov al,1`; receive MAC check `jnz 0x8a67ee` -> NOPs; receive decrypt
  `0x8a683f`-`0x8a6859` -> `rep movsb` src r14 -> dst `[rbp-0x3b8]`, length r15d. Handshake and the (unchecked) MAC
  stay. Two PCs over Steam (2026-10-29 02:59): public FFA on Raid with Pete's Windows build, no errors. Earlier:
  two patched instances on one PC matchmade and played Hardcore FFA on Drone; strace shows readable
  payloads both ways (counters, `01` padding). Packet: 6-byte header, 8-byte MAC, u16 payload length, payload
  padded to 8. Patched and unpatched games can't talk.
- **Plain peer data, PS3 done (2026-10-29):** RPCS3 fork patch 0009 (built in, also online). PS3's bdDTLSData
  doesn't 3DES inside: send `0x7fc788` / receive `0x7fcb80` XOR each 8-byte block with an 8-byte value from the
  caller, and receive compares the MAC (`memcmp(hdr+10, mac, 8)`). Patch: `xor` -> `nop` at `0x7fca5c`/`0x7fca74`
  (send) and `0x7fcd88`, `xor r3,r5,r3` -> `mr r3,r5` at `0x7fcda8`, MAC `bne` `0x7fcd4c` -> `nop` (receive).
  Tested with two RPCS3 copies on one PC: matchmaking, lobby and party messages work; packets readable
  (`partyaccept`, `profiles`, `getchallenge`: the in-game connect also runs inside DTLS DATA). The match itself
  doesn't start on one PC: the host never finishes loading, so the joiner times out ("Lost connection to host").
  The unpatched official RPCS3 fails the same way in the same setup (and its DATA has no readable text), so it is
  the one-PC CPU limit, not the patch. **Two PCs (2026-10-29 05:39, Linux host + Windows member over Steam):
  Team Deathmatch on Yemen ran with the patch on both sides**, full bars, traffic readable in the bridge dump.
- **Byte order (from the captures):** the DTLS header and the u16 length are little-endian on **both** builds (PS3
  swaps them explicitly), e.g. sequence `01 00`. So the DTLS layer needs no translation. The payload is native:
  PS4 `57 04 ...`, PS3 `04 57 ...` (same u16 0x0457). Translation starts inside the payload (layers 2 and 3).
- **DTLS handshake is identical too:** INIT 16, INIT_ACK 38, COOKIE_ECHO 189, COOKIE_ACK 114 bytes on both; the
  bdAddr blob in INIT_ACK has the IP and a little-endian port on both (`7f000002 040c` = 127.0.0.2:3076). The
  bridge passes the handshake through and only translates DATA payloads.
- **Payload frame (2026-10-29):** `u16 0x0457` (MSG_WriteShort, native order), `u8 (chan << 4) | sock`, then the
  message. **PS3 appends a 2-byte checksum, PS4 doesn't:** RFC 1071 Internet checksum (sum of big-endian u16
  words, carries folded, complemented; an odd last byte is added unshifted) over the message after the 3-byte frame,
  stored big-endian. PS3 send `0x463318` (checksum `0x334244`), receive `0x463144` -> check `0x334158` (drops the
  packet when it doesn't match); PS4 send `0x32db70`, receive `0x32da20` (no checksum). Verified on all 260 whole
  PS3 packets captured. So PS3 -> PS4: drop the checksum, swap the u16; PS4 -> PS3: swap, append the checksum.
- **Messages:** lobby/party traffic is out-of-band (`ff ff ff ff` + command), the same command set on both:
  `hostAnnounce`, `ph`/`pha` (party heartbeat/ack), `pseg`, `psack`, `go <...> <map> <mode>`, `joinParty`,
  `partyaccept`, `member`, `memberJoin`, `profile(s)`, `profileack`, `profilesack`, `findbest`, `vt`, `disf`,
  `getchallenge`, `challengeResponse`, `connect`, `connectResponse`, `stats`, `statresponse`, and binary `b`. Text
  commands have the same syntax; binary bodies are native-endian structs of different sizes (e.g. `ph` 26 bytes
  on PS3, 40 on PS4). In-game traffic is sequenced netchan data (huffman; layer 3). Captures + decoder:
  `crossplay/st_dtls.py` in the RE folder (strace sendto logs of the patched games).
- **Party member command table** (same 19 commands, same order on both): PS3 `0x8fb594` (12-byte entries, name +
  function descriptor), PS4 `0xc03fc0` (24-byte entries). Handlers PS3 / PS4: pha 153ba0/154700, psack
  15404c/1548a0, joinParty 154588/154c00, memberJoin 154c0c/155180, localJoin 1554d0/155650, member 155bd0/155a90,
  echoreq 153aa0/155b70, finishedloadingdemo 1538e4/155bd0, dis 155ff4/155ce0, leaderdis 15616c/155e30, ihear
  155d24/1564b0, canthear 155e64/156600, profile 156604/156700, profilesack 1567b8/156840, pgs 156968/156a60, pkick
  156968/156a70, leaguestats 1569e0/156a80, leagueoutcomesack 156bd8/156c40, emblemupdate 156d70/156d70.

- Packet types (dispatcher `0x8a3090`): 1 INIT, 2 INIT_ACK, 3 COOKIE_ECHO, 4 COOKIE_ACK, 5 ERROR, 6 DATA.
- ECC (`0x8ce8c0`): libtomcrypt `ecc_make_key(yarrow, 28)` = NIST P-224, a new key per association; public key
  is `ecc_export` (DER: flags, key size, x, y), the secret is the 28-byte x coordinate.
