# Mario Kart 8 Deluxe (Switch)

Title ID: `0100152000022000`. Supplied base container v0, installed update v1507328 (**4.0.1**). Booster Course DLC was not installed for these tests.

## Current result — 2026-11-10

**Two isolated game instances joined the same Eden transport room, discovered each other through Wireless Play, and started a two-player race at Mario Kart Stadium. Keyboard driving worked on each instance, and the remote kart movement appeared on the other screen.** Both logs recorded successful automatic room joins; LDN states reached host 3 and guest 5. Neither log contained a critical error or a null-PC exception during this test. A complete race finish, physical controllers, and a two-PC Steam relay test remain unverified. The user requested local testing because a second PC was unavailable.

Validated setup: USCL-patched Eden v0.2.1 graphical frontend, matching official v0.2.1 room server, update 4.0.1, firmware **22.5.0**, and the existing compatible keys. The two game profiles had separate configs, NAND saves and logs. Installed game/firmware content was shared through content-directory links; no content installations ran during the test. The normal installed USCL applications and real player profiles were not used.

USCL route: host a Steam session, join the private loopback Eden room over UDP 24872, then choose **Wireless Play** in the game. One player creates the game's room; the other selects it. Match emulator, game-update and DLC versions. Nintendo's Online Play service is not used.

## Fixes required

- The original Mii-selection failure cleared with decryptable firmware assets. Firmware 23.0.1 had been downloaded but was not installed during initial tests; after installation, its MiiModel and SystemVersion archives could not be decrypted by the existing keys. Eden continued substituting placeholder Mii assets.
- The subsequently supplied 22.5.0 firmware decrypts correctly. Eden identifies version 22.5.0, loads genuine Mii models, and proceeds into gameplay. This is a tested sufficient version, not a demonstrated absolute minimum.
- The supplied update CNMT declares RequiredSystemVersion **23.0.1**, while its local NCA containers use key generation 4. This console requirement does not establish Eden's minimum system-archive version. Firmware 23.0.1 uses generation 23 for the inspected system archives and needs revision 16 key material missing from the current set; firmware 22.5.0 uses generation 22 and works with the supplied keys. Key values were never published.
- Upstream Eden v0.2.1 SDL advertises `--multiplayer` but omits `Network::Init()`. It reports `Network isn't initialized` / `Could not access RoomMember`. The SDL patch fixes this and two SDL clients joined a room, but visible updated-game rendering in that frontend remains unresolved.
- The working graphical frontend now accepts USCL's `--uscl-room NAME@127.0.0.1:PORT`, joins before boot, and cancels unsuccessful online starts. Its patches and exact base are in [uscl-eden](../uscl-eden/README.md).
- Qt keyboard key codes and SDL scancodes differ. USCL preserves the graphical settings file and generates separate translated SDL settings for alternative CLI launches, including nested keyboard-stick bindings. The graphical route uses native Qt bindings directly.

## Verification and limitations

The actual dedicated room server hosted two real game clients. In-game discovery, connection, course voting, race loading and driving passed locally. The actual USCL desktop game entry also created a Steam session, started its room server, and launched the patched graphical core with a confirmed automatic room join. The final desktop retest reached the main menu using keyboard L+R with only the game window open; automatic room-chat popup suppression preserved input focus. The preview needed its Steam runtime library path set; forced native Wayland needed the tested XWayland fallback. This is not an end-to-end two-PC relay test. No friend was invited or contacted during local validation.

The shell build, self-test, QML startup smoke test, and previous 21 Rust bridge unit tests cover the integration scaffolding. Linux is the only platform tested here. The regular release does not bundle the patched core; the desktop Switch preview selects the development build when available.

Earlier base-game tests without usable firmware encountered an NVMap page-mapping assertion and an invalid instruction address. These historical failures do not describe the working updated-game graphical setup.

See [Switch setup](../docs/SWITCH.md) for configuration and [the pinned core build](../uscl-eden/README.md) for reproduction.

## Independent Online Play service — in progress

A separate [USCL backend](../uscl-switch-online/README.md) now supports temporary players and compatible public/invite rooms. Backend tests exercise two-client discovery/join, compatibility, capacity, invitation protection and expiry. The graphical emulator has an explicit headless private-service probe; successful negotiation reports `native_online_play: false`. This does not establish game-menu compatibility. Native account/friend service adapters, game-facing protocol support and a native-menu race have not been implemented or validated. No Nintendo service credentials or endpoint redirections are used.

Native-menu diagnostic on the working 4.0.1 / firmware 22.5.0 setup: selecting Online Play produced **2306-0520**. Before the error, account calls used `EnsureIdTokenCacheAsync` / `LoadIdTokenCacheDeprecated` stubs; `sfdnsres` explicitly returned `EAI_AGAIN` for the game-server hostname. This is emulator-side hostname rejection, not proof of incorrect PC DNS. The separate private backend has no native game protocol adapter yet. The error-applet transition subsequently logged texture-cache “Unregistering unregistered page” assertions; these occurred after the lookup failure and are an additional emulator issue, not evidence of successful matchmaking. This diagnostic used the existing Wireless Play core; the new probe does not change guest services or hostname handling.

Follow-up with Eden patch 0005: an opt-in, exact-title/exact-template NSD route reached a local TCP 443 observer through the real Online Play menu. The observer received a 1,551-byte first chunk with a TLS record header declaring 1,546 bytes, then closed without a reply. The game displayed **2306-0502**. No application request was decrypted and no native room/login/race passed. REA captured the process lifecycle; the local observer, screenshot and trimmed emulator log establish the separate network/UI observations. [Evidence, checks and reproduction](../uscl-switch-online/NATIVE-DIAGNOSTIC.md). The working Wireless Play route is unchanged; this follow-up did not repeat its two-client race.

Subsequent diagnostic TLS termination exposed a 156-byte HTTP GET to `/` with WebSocket upgrade/version-13 headers. The strict adapter rejected its key under the standard nonce check; the value was not logged. This remains an unresolved emulator/game handshake boundary, not native compatibility. No real-game binary frame or authentication method was observed. Synthetic TLS/WebSocket/Lite framing tests pass separately.
