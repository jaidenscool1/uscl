# Call of Duty: Black Ops II (BLUS31011)

`np-profile.py`: PARTIAL (disc 1.00, profiled 2026-10-23). Basic 14, Trophy 10, Manager 9, Lookup 7.
No Matching2, no Signaling. Also imports `sys_net`, `cellHttp`, `cellHttpUtil`, `cellSsl`, `cellNetCtl`.

## How it plays online
Matchmaking, lobbies, stats and NAT traversal are on Activision's **Demonware**, not PSN. PSN is used for:
- login proof: `sceNpManagerRequestTicket2` / `GetTicket`. Demonware checks this ticket. An RPCN ticket isn't
  signed by Sony, so the official servers are expected to refuse it (not tested yet).
- friends + presence: `GetFriendListEntryCount`, `GetFriendPresenceByIndex2`, `SetPresenceDetails2`
- invites: `SendMessage`, `SendMessageGui`, `RecvMessageCustom`, `GetMessageEntryCount`

The game traffic itself is peer to peer between consoles, arranged by Demonware, over `sys_net`.

## Tested 2026-10-23 (1.19, RPCN, one PC)
At boot, without any menu input, the game resolves `ops2-ps3-auth.prod.demonware.net` (185.34.107.28) and
`cod7-stun.{us,eu,jp,au}.demonware.net`, gets an RPCN ticket (`sceNpManagerRequestTicket2`, service
`UP0002-BLUS31011_00`) and connects to auth on TCP 3074. The server drops it, and it repeats every few seconds
with a new ticket. It also talks UPnP to the router. Multiplayer → Play Online: "Connecting to Online Service",
then "The Call of Duty: Black Ops II server is not available at this time." So Demonware is up but refuses
RPCN tickets. The Multiplayer menu also has a second entry that looks like **LAN Party** (being checked).

## Plan: our own Demonware (decided 2026-10-23)
LAN Party (Create / Join, UDP 3074 + 3075 with SO_BROADCAST) would give matches only. Friends, invites, parties,
stats and the online menus all live on Demonware, so the player chose a full stand-in, backed by Steam.

Base: **open-bitdemon-emulator** (github.com/Laupetin/open-bitdemon-emulator, Rust, AGPL-3.0 like RPCN, active).
It speaks the BitDemon protocol, has auth + lobby services (storage, profile, rich presence, counters, groups...),
and already lists `T6Ps3` (BO2 PS3, title 18396). Its only auth handler is Steam (PC). `Ps3ForMmpRequest` (0x12)
is defined but not handled. Kept as a fork shared as patches, like uscl-rpcn.

1. **PS3 auth.** Handle `Ps3ForMmpRequest`: read the NP ticket, issue a DW ticket the game accepts. Needs the
   exact reply format and how the PS3 client derives its session key. Reverse engineer it from the decrypted 1.19
   EBOOT (bdAuth code). Done when BO2 gets past "Connecting to Online Service".
2. **Redirect.** IP swap list: `ops2-ps3-auth.prod.demonware.net`, the lobby host it is given, and
   `cod7-stun.*.demonware.net` → 127.0.0.1. The host runs the stand-in; members reach it through bridge forwards
   (`host bo2`, like `host skate3`).
3. **Lobby services the menus need** (storage/profile/stats/rich presence): whatever BO2 asks for, in the order
   it asks, until the online menu opens.
4. **Steam-backed social:** friends = Steam friends, invites/party = the Steam session, presence = Steam rich presence.
5. **Matchmaking + game traffic:** sessions from the Steam lobby. Player addresses handed out (and returned by a
   STUN stand-in) as 127.0.0.1:39000+slot, so game UDP 3074 goes over Steam the same way Minecraft's does.

## Anti-cheat (player's requirement: no cheaters like on today's servers)
Designed in from the start, on our server's side, because a client-side check in an open emulator can be patched out:
- **Identity = Steam account.** Bans go on the Steam ID, so a ban isn't undone by making a new RPCN/PSN name.
- **The game's own challenges.** BO2 has Demonware anti-cheat built in (`live/live_anticheat_mipster.cpp`,
  `LiveAntiCheatAnswerChallenges`, `challengeResponse`): the server sends challenges and the game answers, e.g. with
  checksums of its own code/memory. Our server can send them and compare answers against an unmodified 1.19.
  libbitdemon already has an `anti_cheat` lobby module to build on. To reverse: the challenge types and answer format.
- **Server-side checks.** Stats, XP, prestige and unlocks are written through our server, so impossible values
  (rank jumps, stats faster than possible) are rejected there, not trusted from the client.
- **Who can join.** Sessions are Steam lobbies (friends-only by default), so public matchmaking with strangers is
  opt-in; reports and bans apply across every USCL game.
- uscl-rpcs3 can report the executable's hash and whether game patches are on. Easy to fake, so it's only a hint.

Built (2026-10-24): Steam-ID kick and ban (host's bridge, lobby data "removed"; every bridge drops a removed
player's traffic), `USCL_ONLINE` (uscl-rpcs3 0006: no game patches, GDB server or logpoints in a session) and the
EBOOT.BIN match between host and joiner. Not yet: the game's own challenges (needs the challenge format reversed)
and stat checks (our Stats service answers "no rows" and stores nothing yet, so there's nothing to check).

## PS3 login, reversed (t6mp 1.19, 2026-10-23)
Ghidra 12 headless, language `PowerPC:BE:64:A2ALT-32addr`, r2 (TOC) = 0xd67e98 set before analysis. Addresses
are in the decrypted `t6mp_ps3f.self`.
- **Key.** Per player, the connect state machine (`0052eaac`, state struct `0x026c0658 + n*0x108`) makes a random
  24-byte key (`008079e4` → `008097fc`) at `+0xd4` and passes it as the **cookie** of
  `sceNpManagerRequestTicket2` (`008de9fc(..., key, 0x18, ...)`). So the PSN ticket carries the client's key.
  RPCN copies the cookie into its tickets as a binary user-data field (`rpcn ticket.rs`), so our server can read it.
- **Request** (`00807a04`, message type `0x12` = `Ps3ForMmpRequest`): type-checked bit, `u32 iv_seed`,
  `u32 title` (T6Ps3 = 18396), `u32 ticket_len`, ticket bytes. If the 5th argument (passed as `0x13`) is non-zero,
  also `u32 8` + 8 bytes: `[0xEFBDADDE][arg]`, 3DES-encrypted with the key, IV from the seed. That proves the
  client holds the key.
- **Reply** (`00807fb4`): `u32 iv_seed`; 152 bytes (0x4c0 bits) of auth ticket, 3DES-CBC-decrypted with the
  cookie key and the IV `Tiger(seed)` (`007e88a4`, `007e8a00`); then 128 bytes of opaque auth proof stored at
  auth`+0x2c` for the lobby server. The ticket is accepted when its magic is `0xEFBDADDE` (`DAT_009b29fc`).
- **Ticket layout** (`00809ad8`): magic u32, type u8, title u32, issued u32, expires u32, license u64,
  user id u64, username [64], session key [24], 3 bytes, 4 bytes. Same as libbitdemon's `AuthTicket` except for
  the trailing bytes (it writes 4) and the padding: BO2 always reads 152 encrypted bytes.
- **So the server side is:** open-bitdemon's Steam reply, but the ticket is encrypted with the cookie key from
  the RPCN ticket (not a client-chosen session key), padded to 152 bytes. Our server picks the session key. It can
  also check the RPCN ticket's signature, since we run RPCN: that ties every Demonware login to a real account.

## Play Online, traced (2026-10-23)
Same error with our Demonware: "server is not available". How it was found: uscl-rpcs3 0002 logpoints (the
official build's GDB breakpoints don't work with LLVM, and pausing trips BO2's 30 s hang watchdog at `0x463058`,
disabled with an RPCS3 patch for debugging), then `strace` of the network calls.
- The click runs Lua `IsFeatureBanned`, `CheckNetConnection` (`00530cb8`, only checks the network link), then the
  console command `initiatedemonwareconnect` (`0052e6f0`: only resets connection state 8 → 1; ours is 6 = lobby
  connected). The error comes 40 s later.
- 1.5 s after the click Demonware's NAT traversal client (`007f57f0` pump → `00800c10` → `007ff490`) starts sending
  a 29-byte type **`0x0e`** packet to `cod7-stun.*.demonware.net` = Activision's live `185.34.107.128:3074`, every
  15 s, and **gets no reply**. NAT type discovery to the same servers works (`1e 02 00` → `1f 02 00 04 <public ip>…`,
  `14 02 00 02` → `15 …` from `.129`), so those servers are alive: they just don't know our sessions.
- Likely cause: the `0x0e` request (a NAT traversal introduction?) needs Activision's server to know our login.
- Fix: host our own `cod7-stun` in uscl-dw (NAT discovery `0x1e`/`0x14` + the `0x0e` reply) and redirect the four
  host names. Next: the `0x0e`/`0x0f` format (builder `008037ec` + `00803854`, reply handling in `00800c10`).
- Also seen in interpreter mode only: the lobby session drops every ~30 s and reconnects (client side, no requests
  in between). Probably just the slow interpreter; check again once the above works.

## Play Online, part 2 (2026-10-23)
- The 16-byte online data file (see `uscl-dw/README.md`) makes BO2 fetch, create and upload `mpstatsCompressed`
  and `mpClassSets`, read profiles and rich presence, and call Teams. The stats gate was `FUN_0055cb5c`
  (online data file loaded + version check), checked by the stats fetch `005540bc`.
- A served `largeheatmap.raw` made the client drop the lobby session every 30 s; without it the session is stable.
- Play Online still fails. Logpoints on every Lua engine call and on C→Lua events (`FUN_00671294`, event name in
  r4) show: before the click C sends `signed_into_live`, `first_signed_in`, `stats_downloaded`,
  `class_sets_downloaded`, …; after the click the menu only polls `CheckNetConnection` (true) and C sends nothing
  for 40 s. The click starts Demonware's NAT traversal client (`0x0e` to cod7-stun, unanswered). (The guess here,
  that the menu waits for the party lobby, was wrong: see part 3.)
- NAT traversal packets are signed: `007ff8a8` hashes with a 28-byte key held by the client. A replacement relay
  needs that key's origin and the reply format. Formats known so far: NAT discovery `1e 02 00` →
  `1f 02 00 <ip 4 BE><port 2 LE>`; `14 02 00 02` → `15 02 00 <your addr><server addr>`; traversal packets
  (types 0x0a–0x13) `type, u16 version, 10 bytes, u32 LE, addr, addr`.

## Play Online, part 3: where it stands (2026-10-23, handoff)
Corrections to part 2, and the current best understanding:
- **The NAT relay is probably not the blocker.** The 28-byte key in `007ff8a8` is random, made locally
  (`007ff600` → `FUN_007eca48(rng, +0x38, 0x1c)`), so no server needs it. The `0x0e` packet's 10-byte field is
  never filled in by its builder (`008037ec`); it looks like a keep-alive to hold the NAT mapping open.
- **Already-connected was not the cause either.** With the connection state forced to 8 before the click (GDB
  write to `0x026c071c`), the click reconnects and C sends `signed_into_live`, `first_signed_in`,
  `stats_downloaded`, `class_sets_downloaded`, yet the menu still times out.
- **What the menu waits for** (read from the loaded menu script in a memory dump taken at the click, uscl-rpcs3
  0003): the `popup_connectingdw` popup (`MENU_CONNECTING_DW`) closes and sends `open_main_lobby_requested` when
  `UIExpression.IsDemonwareFetchingDone(controller)` and `Engine.IsSignedInToDemonware` are true; otherwise it
  fails after `CONNECTINGDW_MAX_WAIT_TIME`, polling `CheckNetConnection` on PS3.
- `IsDemonwareFetchingDone` is UI expression #321 in the name table at `0xd7be50`. The status it uses is built by
  `00507950`: a bitmask of online checks compared with a required mask (`0x1bee` multiplayer, `0x11ee` Zombies).
- **Next step:** find which bits of that mask are still missing with our server (read the flags from a memory dump
  taken at the click), then make the server supply what each missing check needs. This session stopped here:
  an automated safety check interrupted the analysis twice at this point, so it was handed off rather than pushed
  further. Whoever continues: keep it to what a private server for an owned copy needs.

## Play Online, part 4: solved (2026-10-23)
`00507950` builds the status bit by bit. Required `0x1bee`: 0x2/0x4 signed in and lobby state 6 (`0x026c0724`,
`0x026c071c`), 0x8 `005516b4`, 0x20 `0xd69e10 == 6`, 0x40 `0x027f3c84`, 0x80 `0xd867d1`, 0x100 online data file
(`0055cb5c`), 0x200 `0xd8674d`, 0x800 `0xd867d4`, 0x1000 `0xd8605d`. In the dump taken at the click, 0x80 and 0x800
were 0. Both are set only by `0055cc24`, which reads the online data wad (header `54 33 77 ab`, timestamp, count,
version; 0x2c-byte entries name[32], compressed size, size, offset; zlib, each under 256 KB):
- `playlists_mp.info` (name from `0037e310`; `_zm` for Zombies) → 0x80, set as soon as the entry exists.
  Parsed by `0037ea88`: line-based, sections `gametype` (with `script`), `playlist <0-199>`, `category`,
  `supercategory`, `maplist`, `settings`; `rule`/`set`/`name`/`icon`/`description` inside them.
- `leagues.info` → 0x800 if `002cd478` accepts it: JSON with `version` ≥ 1 and at least one entry in `leagues`
  and in `divisions` (unknown keys skipped; bad `bonus_time` dates, `seasons`, `elo_awards` or `icons` fail it).
  Also read: `nouns`, `numbers`.
- Optional entries the same function looks for: `message_encryption.dat`, `motd-mp-<lang>.json`,
  `voting-mp.json`, `codtv-mp.json`, `youtube.info`, `zdedicatedpingtest.csv`.
Our files are in `uscl-dw/bo2-wad/` (`mkwad.py` builds the wad). With them **Play Online reaches the lobby**
(user test, 1.19, one PC). The playlist is a first guess (TDM, three maps): check what the menu offers and
whether a match starts. New in the log: `Tried to call unknown service 32`, and one file listing failing with
"number too large to fit in target type".

## Playlists, part 5 (2026-10-23)
`uscl-dw/bo2-wad/playlists_mp.info`: Core, Hardcore, Party Games and a USCL category (25 playlists, 14 base maps).
Our own file (Activision's original isn't available); format read from `0037ea88` and checked in game memory:
- Blocks: `supercategory <id>`, `category <id>` (with `supercategory <id>`), `gametype <id>` (with `script <mode>`
  and `rule <console command>` lines, e.g. `rule setgametypesetting hardcoreMode 1`), `maplist <id>` (one map per
  line), `playlist <0-199>` (`name`, `description`, `category`, `maxparty` ≤ 18, `minparty`, `ranked`, ...).
  Define supercategories and categories before the playlists that use them: the counts the menu needs are
  updated when a playlist names its category.
- Rotation entries inside a playlist are **comma-separated**: `<map or maplist>,<gametype id>,<weight ≥ 1>`
  (the tokenizer switches to CSV mode there: `003e33ac(1)`). With spaces the line is one token and is dropped.
- Public matchmaking shows only (super)categories with `filter playermatch` (the lobby compares
  `UIExpression.PlaylistCategoryFilter` with it; other values: `leaguematch`, `wagermatch`, `solomatch`).
- `name` and `description` take a language first: `name english "Core"`. Without it the line is skipped.
- The menu (`GetPlaylistSuperCategories` `00383de8`, `GetPlaylistCategories` `003843d4`, `GetPlaylists`
  `003840c8`) hides playlists with no entries and (super)categories with no playlists.
- Memory: playlists `0x01c663c8` (0x60 each; +0x14 category, +0x18 first entry, +0x1c entry count), entries
  `0x01c523c8` (0x14 each; count `0xd7bd34`), categories `0x01c6aec8` (0x48), gametypes `0x01c6c6d0` (0x10).
- Reading memory from the official RPCS3 build: its GDB server freezes the game when the client disconnects, so
  keep one connection open (raw `m` packets) for the whole session, and send `c` afterwards: connecting pauses.

## Over the session tunnel (plan, 2026-10-24)
Goal: two PCs, any OS, only 127.0.0.1 on members.
1. **Login / lobby / stun on 127.0.0.1** (done, uscl-dw 0008, tested on one PC: NAT Open, lobby works). Members
   forward TCP 3074 to the host (`host tcp:3074`).
2. **Game traffic** (done in uscl-bridge, untested across PCs): P2P frames carry the sender's local port and are
   delivered to the same port (3658 for RPCN games, 3074-3079 for Demonware titles; nothing else).
3. **Advertised address** (done, untested across PCs): `uscl-bridge host bo2` carries members' NAT discovery out of
   their slot port (`sudp:` forwards), so stun reports 127.0.0.1:39000+slot, the address everyone reaches them
   at; `DW_STUN_SELF_ADDR=127.0.0.1:39001` does the same for the host's own game. Same-NAT check: `007ea608`
   compares public addresses with `007e9e98`, which compares the **port** too, so members (different slot ports)
   are never "same NAT" and peers use the public address. No game patch needed.

Two-PC test (host = Steam lobby owner):
- host: RPCN with `USCL_LOCAL=1` on 31413; `DW_ADDR=127.0.0.1:3074 DW_STUN_ADDR=127.0.0.1:3074
  DW_STUN_ALT_ADDR=127.0.0.1:3077 DW_STUN_SELF_ADDR=127.0.0.1:39001 dw-server`; `uscl-bridge host bo2`.
- member: `uscl-bridge join`. Both: RPCS3 RPCN host 127.0.0.1, the 127.0.0.1 IP swap list from `uscl-dw/README.md`,
  bind address 0.0.0.0. Both bridges must be this version (P2P frames now carry the port).
