# Call of Duty: Black Ops II (BLUS31011)

`np-profile.py`: PARTIAL (disc 1.00, profiled 2026-10-23). Basic 14, Trophy 10, Manager 9, Lookup 7.
No Matching2, no Signaling. Also imports `sys_net`, `cellHttp`, `cellHttpUtil`, `cellSsl`, `cellNetCtl`.

## How it plays online
Matchmaking, lobbies, stats and NAT traversal are on Activision's **Demonware**, not PSN. PSN is used for:
- login proof: `sceNpManagerRequestTicket2` / `GetTicket`. Demonware checks this ticket. An RPCN ticket isn't
  signed by Sony, so the official servers are expected to refuse it (not tested yet).
- friends + presence: `GetFriendListEntryCount`, `GetFriendPresenceByIndex2`, `SetPresenceDetails2`
- invites: `SendMessage`, `SendMessageGui`, `RecvMessageCustom`, `GetMessageEntryCount`

The game traffic itself is peer to peer between consoles, arranged by Demonware, over `sys_net`.

## Tested 2026-10-23 (1.19, RPCN, one PC)
At boot, without any menu input, the game resolves `ops2-ps3-auth.prod.demonware.net` (185.34.107.28) and
`cod7-stun.{us,eu,jp,au}.demonware.net`, gets an RPCN ticket (`sceNpManagerRequestTicket2`, service
`UP0002-BLUS31011_00`) and connects to auth on TCP 3074. The server drops it, and it repeats every few seconds
with a new ticket. It also talks UPnP to the router. Multiplayer → Play Online: "Connecting to Online Service",
then "The Call of Duty: Black Ops II server is not available at this time." So Demonware is up but refuses
RPCN tickets. The Multiplayer menu also has a second entry that looks like **LAN Party** (being checked).

## Plan: our own Demonware (decided 2026-10-23)
LAN Party (Create / Join, UDP 3074 + 3075 with SO_BROADCAST) would give matches only. Friends, invites, parties,
stats and the online menus all live on Demonware, so the player chose a full stand-in, backed by Steam.

Base: **open-bitdemon-emulator** (github.com/Laupetin/open-bitdemon-emulator, Rust, AGPL-3.0 like RPCN, active).
It speaks the BitDemon protocol, has auth + lobby services (storage, profile, rich presence, counters, groups...),
and already lists `T6Ps3` (BO2 PS3, title 18396). Its only auth handler is Steam (PC). `Ps3ForMmpRequest` (0x12)
is defined but not handled. Kept as a fork shared as patches, like uscl-rpcn.

1. **PS3 auth.** Handle `Ps3ForMmpRequest`: read the NP ticket, issue a DW ticket the game accepts. Needs the
   exact reply format and how the PS3 client derives its session key. Reverse engineer it from the decrypted 1.19
   EBOOT (bdAuth code). Done when BO2 gets past "Connecting to Online Service".
2. **Redirect.** IP swap list: `ops2-ps3-auth.prod.demonware.net`, the lobby host it is given, and
   `cod7-stun.*.demonware.net` → 127.0.0.1. The host runs the stand-in; members reach it through bridge forwards
   (`host bo2`, like `host skate3`).
3. **Lobby services the menus need** (storage/profile/stats/rich presence): whatever BO2 asks for, in the order
   it asks, until the online menu opens.
4. **Steam-backed social:** friends = Steam friends, invites/party = the Steam session, presence = Steam rich presence.
5. **Matchmaking + game traffic:** sessions from the Steam lobby. Player addresses handed out (and returned by a
   STUN stand-in) as 127.0.0.1:39000+slot, so game UDP 3074 goes over Steam the same way Minecraft's does.
